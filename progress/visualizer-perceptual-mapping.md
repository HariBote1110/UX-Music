# ビジュアライザーのバー高さマッピングを聴覚特性ベースに刷新

## 決定
- Goバックエンドからの周波数バイト配列（dBスケール済み、正規化済み、0-255）は正しくなったが、旧来のバー高さ計算（中心ビンサンプリング＋pow(1.4)＋sine乗数＋対称0.4/0.6スムージング）は「動きはするが聴感と合わない」状態だった。原因を切り分け、次の5点に置き換えた。
  1. **連続対数バンドのビン平均**: 6バーの境界を `[40, 150, 450, 1400, 4000, 9000, 16000]` Hzとし、各バーは自身の帯域に入る全ビンを平均する（中心ビン±固定レンジのサンプリングをやめ、帯域を取りこぼさない）。
  2. **ノイズフロアゲート＋レンジ拡張**: `v = avg/255` を `u = max(0, (v-0.22)/(1-0.22))` でゲートし、有効レンジを0-1へ再マップ。
  3. **dB領域向けのゆるいカーブ**: `pow(u, 1.1)` のみを適用。旧来の `pow(1.4)` は、すでにdB変換で圧縮済みのデータへさらに強い非線形をかける二重圧縮になっており、静かな部分が潰れて聴感と乖離していた。
  4. **等ラウドネス補正**: バンドごとのゲイン `[0.9, 1.0, 1.05, 1.15, 1.25, 1.35]` を乗算（上限1.0でクランプ）。低音をやや抑え、ハイハットやシンバルなど高域が視覚的に動くよう高音を持ち上げる。
  5. **非対称アタック/リリース**: `target = value*16 + 4` (px) に対し、上昇時は係数0.55（速い）、下降時は係数0.18（遅い）で補間。旧来の対称0.4/0.6ブレンドは立ち上がりと減衰が同じ速さになり、パーカッシブな音の「叩き」感が出なかった。フレームレート非依存化のため、係数に `min(2, dtMs/16.7)` を乗じる（rAFタイムスタンプ差分を使用、初回フレームは係数そのまま）。
- 中央バーを強調していたsine乗数は撤去。実際のスペクトル形状がそのまま反映されるようにした。
- 上記のマッピングを純粋関数 `computeBarHeights(sourceData, sampleRate, fftSize, lastHeights, dtMs)` として `src/renderer/js/features/visualizer-mapping.ts` に切り出し、DOM/Wailsブリッジへの依存を断ってvitestで単体テスト可能にした（`visualizer.ts` を直接importするテストは `bridge.ts` の `window.electronAPI` 未定義でモジュール読み込み時に例外を起こすため、切り出しが必須だった）。

## 代替案として検討したもの
- **pow(1.4) を維持する案**: 却下。バイトデータがすでにdB変換で対数圧縮されているため、その上にさらに強いべき乗カーブをかけると小さな音がほぼ0に潰れ、「動きが音と合わない」というユーザー報告の一因になっていた。dBスケール前提でカーブをごく弱く（1.1）に留めるのが妥当と判断。
- **中心ビン＋可変レンジのサンプリングを維持する案**: 却下。帯域境界付近のエネルギーが計算から漏れる／二重カウントされるケースがあり、実際のスペクトル形状と表示がずれやすい。帯域全体を連続的にカバーする平均に変更。

## 制約・注意点
- `lastHeights` 配列は `computeBarHeights` 内で破壊的に更新される（呼び出し側の状態を直接書き換える設計）。テストでは配列を渡してフレームをまたいだ呼び出しを行うことで連続再生をシミュレートしている。
- `visualizer.ts` 側は `lastDrawTimestamp` を新設し、`startVisualizerLoop()` でリセットしている（曲の再開時にdtMsが不自然な大きな値にならないようにするため）。

## 追記: 帯域別AGC（自動ゲイン）導入で上張り付きを解消

### 決定
- 実音源では上記マッピング後の値（ノイズゲート＋等ラウドネス補正後の `u`）が0.7〜1.0付近にほぼ張り付き、バーが常に上限近くで数px程度しか動かない問題が判明した。Go側のdBマッピング（-100〜-30dB）では音楽の実効エネルギーがレンジの上端付近に集中するため、固定の閾値・カーブだけでは絶対値ベースの表現にしかならず、相対的なダイナミクスが失われていた。
- 対策として、各帯域が自身の直近ピークに対して正規化される**帯域別AGC（自動ゲインコントロール）**を導入した。
  1. **永続状態をオブジェクト化**: `computeBarHeights(sourceData, sampleRate, fftSize, lastHeights, dtMs)` を `computeBarHeights(sourceData, sampleRate, fftSize, state, dtMs)` に変更し、`state = { lastHeights: number[6], envelope: number[6] }` とした。ファクトリ `createVisualizerState()` を追加し、`lastHeights` は4px、`envelope` は `ENV_FLOOR`(0.25) で初期化する。`visualizer.ts` 側は `lastHeights.fill(4)` していた3箇所（ループ開始・停止・IntersectionObserverによる非表示化）を `visualizerState = createVisualizerState()` による再生成へ置き換えた。
  2. **エンベロープ追跡**: 等ラウドネス補正後の値 `u` に対し、`u > envelope[i]` なら即座に追従（アタック瞬時）、そうでなければ半減期4秒 (`Math.pow(0.5, dtMs/4000)`) で減衰させ、`ENV_FLOOR` を下回らせない。無音・静かなパッセージでノイズが増幅されないようにするための床。
  3. **相対値への正規化＋コントラストカーブ**: `n = min(1, u / envelope[i])` で直近ピーク比の相対値を作り、`out = pow(n, 1.6)` でコントラストを強調してから、既存の `out*16+4` px マッピングとアタック/リリース非対称スムージングに渡す。
  4. **ノイズゲートは維持**: `u <= 0`（ゲートされた状態）ではエンベロープ更新自体をスキップし `out = 0` とする。無音がエンベロープを持ち上げることはない。

### 代替案として検討したもの
- **固定dBウィンドウを狭める案（例: -60〜-30dBだけを使う）**: 却下。静かなマスタリングの曲や別ジャンルでは音楽エネルギーの分布が変わるため、固定窓ではすぐに破綻する。曲ごと・帯域ごとに変化する実際のダイナミクスに追従できるAGCの方が汎用性が高いと判断した。

### 制約・注意点
- `state.envelope` は帯域ごとに独立して追跡されるため、低音だけが鳴っている曲では高音バーのエンベロープが `ENV_FLOOR` に留まり続け、次に高音が鳴った瞬間は強く反応する（意図した挙動）。
- テストでは `createVisualizerState()` を都度生成し、フレームをまたいで同じ `state` を渡すことで連続再生を再現している。大きな `dtMs`（例: 12000ms）を1フレームだけ渡すことでエンベロープの長時間減衰をシミュレートするテストパターンを追加した。

## 追記: エンベロープ立ち上がりの平滑化＋ヘッドルームで伸び切りを抑制

### 決定
- 帯域別AGC導入後も「伸び切りが酷い」という指摘があった。原因は、エンベロープのアタックが**瞬時追従**（`u > envelope[i]` なら `envelope[i] = u` に即代入）だったこと。これだと現在フレーム自身がエンベロープの基準値になってしまい、正規化値 `n = u/envelope` が恒常的に1に張り付き、`pow(1.6)` を通しても1のままでバーが常に上限20pxに達してしまっていた。
- 対策として2点を変更した。
  1. **エンベロープ立ち上がりの平滑化**: 瞬時代入をやめ、半減期250ms (`ENV_RISE_HALF_LIFE_MS`) の指数平滑に変更: `envelope[i] += (u - envelope[i]) * (1 - pow(0.5, dtMs/250))`。減衰側（半減期4秒）は変更なし。これにより、単発の突発音（トランジェント）はエンベロープの追従が間に合わず一瞬だけ `n` が1を超えて上限まで振れる一方、持続音はやがてエンベロープに追いつかれて頭打ちになる。
  2. **ヘッドルーム係数**: `n = min(1, u / (envelope[i] * HEADROOM))`、`HEADROOM = 1.2` とした。エンベロープに収束した持続音は `n ≈ 1/1.2 ≈ 0.83`、`pow(1.6)` 後は `≈0.75` となり、上限の少し手前（16px前後）に落ち着く。上限20pxはトランジェントのみが到達する領域として残した。
- ゲート・帯域ゲイン・コントラスト指数1.6・アタック/リリースのpxスムージングは変更していない。

### 代替案として検討したもの
- **コントラスト指数やヘッドルームだけを調整する案**: 却下。エンベロープの瞬時追従を残したままでは、`n` が構造的に1へ張り付く問題自体は解消されないため、根本原因である立ち上がりの平滑化が必須と判断した。

### 制約・注意点
- 立ち上がり半減期250msは減衰半減期4000msよりずっと短い。突発音への反応性を保ちつつ、持続音では数百ms〜1秒程度でエンベロープが追いつき頭打ちになるバランスとして選定した。
- 既存テスト「recovers upward once the envelope decays」は、エンベロープ立ち上がりのプライミングフレーム数を5→60に増やして調整した。5フレームのままだと、エンベロープがまだ収束しておらずトランジェント的な挙動（`n`が1に張り付く）が混入し、意図していた「定常状態での抑圧」を計測できていなかったため。
