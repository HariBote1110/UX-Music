# リモート曲一覧の重複除去（`GET /v1/remote/songs`）

## 背景・観測された重複パターン

「アルバム内の曲が重複することがある」報告を実ライブラリで調査したところ、`library` ストア自体に同一トラックの重複エントリが存在していた。

- CD Rips ステージングディレクトリ（`/Users/yuki/doc/uxmusic/CD Rips/<Artist>/09 - X.flac`）に登録された古いエントリと、整理後のアルバムフォルダ（`/Users/yuki/doc/uxmusic/<Artist>/<Album>/09 - X.flac`）に登録された新しいエントリが両方ストアに残っている（再スキャン時にファイルが移動・整理されても旧登録が消えない）。
- 同一アルバムフォルダ内に同じ曲を2回リッピングしたファイルが異なるファイル名で存在し、一方は `discNumber: 1`、もう一方は `discNumber: 0`（タグ欠落時のデフォルト）で登録され、`fileSize` もわずかに異なる。
- 古い（レガシー）エントリは `id` がファイルパス文字列そのもの、新しいエントリはUUID形式の `id` を持つ。ID生成方式が世代によって異なることが重複判別の手がかりになる。

## 決定：APIレイヤーでの重複除去（ストア非破壊）

`library` ストアそのものを書き換えて重複行を削除するのではなく、`GET /v1/remote/songs` のレスポンス生成時（`server/app_remote.go` の `remoteSongsHandler`）に限定して重複除去をかけることにした。

理由:
- ストアを直接クリーンアップすると、誤判定時に正規のライブラリデータを失うリスクがある。
- デスクトップアプリはストアを直接参照する別経路のため、ここを触るとデスクトップの挙動まで変わってしまう。TV/モバイル等リモートクライアントの表示問題に対して影響範囲を最小化したい。
- 将来的にライブラリ本体のクリーンアップ（スキャナー側でのコンテンツベース重複検出・実ファイル整理）を行う余地を残せる。

既存の `ensureRemoteTrackOrder`（`server/app_remote_songs_order.go`）と同じ「純粋関数＋レスポンス直前の後処理」パターンを踏襲し、`server/app_remote_songs_dedup.go` に `dedupRemoteSongs` を新設した。`remoteSongsHandler` では `dedupRemoteSongs` を `ensureRemoteTrackOrder` より前に適用する（トラック番号の自動採番は重複除去後の実データに対して行うのが自然なため）。

## 重複判定キーと優先順位ルール

判定キー（すべて正規化して連結）:
- タイトル：小文字化＋前後空白トリム
- アルバム／アーティスト：同様に正規化
- トラック番号：`trackNumber`（JSON数値は `float64` で来るため `remoteIntField` で int へ丸める）
- ディスク番号：`max(discNumber, 1)` に正規化（`discNumber: 0` はタグ欠落によるデフォルトとみなし、本当のディスク1と同一視する。真の複数ディスク作品はディスク1とディスク2で別キーになり、両方残る）

対象は `songHasLocalAudio(song)` が true のエントリのみ。YouTube由来（`type: "youtube"`、ローカル音声を持たない）エントリは重複除去の対象外とし、そのまま通過させる（embed/中継専用エントリはローカルファイルの重複問題とは別物のため）。

同一キーが衝突した場合の優先順位:
1. `id` がUUID形式（長さ36かつハイフン4個）のものを、パス文字列などレガシー形式より優先して残す。
2. 両方UUID（またはUUIDが優劣つかない）の場合は `fileSize` が大きい方を残す。
3. それでも同点なら、出現順で先に見つかった方を残す（安定ソート）。

出力順は元の相対順序を保つ（除去されたエントリの位置に後続エントリが繰り上がる形ではなく、残存エントリの元の並び順をそのまま維持）。

## テスト

`server/app_remote_songs_dedup_test.go` にテーブル駆動テストを追加（UUID優先、disc 0/1同一視、真の複数ディスクは両方残る、トラック番号違いは両方残る、タイトルの大小文字・空白差異は同一視、YouTubeエントリは対象外、fileSize比較、同点時は先頭優先、出力順保持）。`go test ./server/` は全件成功。
