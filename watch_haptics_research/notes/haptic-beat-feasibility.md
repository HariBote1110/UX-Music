# Watch 触覚ビート同期の実現可能性（実機実験・仮説記録）

## 目的 / 仮説

ユーザー要望「曲に合わせて揺らす」（設定でオン/オフ）の本実装前に、watchOS の触覚 API が
ビート同期に耐えるかを実機で確かめる。ビート位置の検出は、実験で使えると分かった後に
iPhone 側で行う方針（ユーザー決定 2026-09-13）。

実験前に立てた仮説と、それを否定する結果:

- **H1: 連続発火の下限間隔** — `WKInterfaceDevice.current().play(_:)` を等間隔で呼ぶと、
  間隔 250ms（240BPM 相当）程度までは体感で抜けなく発火する。
  - 否定条件: 250ms 以上の間隔でも振動が抜ける／まとめられる、または呼び出しが無視される。
- **H2: 再生との共存** — AVPlayer でスピーカー／Bluetooth 再生中に振動させても、
  音の途切れ・ダッキング・セッション割り込み（`interruptionNotification`）は起きない。
  - 否定条件: 振動のたびに音量が下がる、音が途切れる、割り込み通知が出る。
- **H3: 画面オフ時の継続** — 音声のバックグラウンド再生中（`UIBackgroundModes=audio`）なら、
  手首を下ろして画面が消えても振動の発火が続く。
  - 否定条件: 画面オフで発火が止まる、または大幅に遅れる（ログの遅延 p95 > 50ms）。
- **H4: タイミング精度** — バックグラウンドキューの絶対時刻タイマーから main に投げても、
  予定時刻からの遅れは p95 で 20ms 未満（ビートとしてズレを感じない範囲）。
  - 否定条件: p95 ≥ 20ms、またはフォアグラウンドでも周期的な大きな遅れが出る。

## 事前に分かっている制約（机上調査）

- watchOS では Core Haptics が使えない（iOS SDK の `CHHapticEngine.h` が
  `API_UNAVAILABLE(watchos)`、WatchOS26.5 SDK に CoreHaptics.framework 自体が無い）。
  使えるのは `WKHapticType` の固定パターンのみ（notification / directionUp / directionDown /
  success / failure / retry / start / stop / click。navigation・underwater 系は専用セッション必須）。
  → 波形の連続変化は不可能。ビート位置での離散的な振動に限られる。
- 連続発火のレート制限は公式ドキュメントに記載なし（Web 検索でも見つからず）。
- Apple Watch 用の触覚メトロノームアプリは存在し、画面オフでも継続をうたうものがある
  （haptik、Silent Beat）。実装方式は非公開。
- リポジトリ内に BPM／ビート検出の実装は無い。`internal/analyzer/analyzer.go` の
  `AnalysisResult.BPM` フィールドは存在するが計算されていない（loudness と energy のみ）。
  触覚関連の既存ノート・棄却記録も無い。

## 手順

- DEBUG 限定の実験画面「Haptics Lab」から、テンポ（BPM）・細分（1拍あたり回数）・
  振動タイプを選んで開始する。
- コンソールの `[HapticLab]` ログで、発火回数と予定時刻からの遅れ（p50/p95/max）、
  アプリ状態（active / inactive / background）を 10 秒ごとに確認する。
- 体感（抜け・まとまり・音への影響）はログに出ないため、ユーザーの報告を結果表に記入する。
- ログの読み方の注意:
  - `lateP50/P95/Max` は「予定時刻 → main 上で `play()` を呼ぶ直前」までの遅れで、物理的な振動の
    時刻ではない（Taptic Engine 側の遅延・間引きはログに現れないので体感で確認する）。
  - `skipped` はタイマーが1間隔以上遅れて起きたときに飛ばしたティック数。遅れたティックを
    連続発火（バースト）させない設計のため、画面オフや main 停止で発火が止まった場合は
    `fired` が増えずに `skipped` が増える。H3 の判定では `skipped` の増え方を見る。

測定マトリクス（各 30 秒以上）:

|---|---|---|---|---|---|
| 1 | 60×1 | 1000 | なし | オン | H1/H4 ベースライン |
| 2 | 120×1 | 500 | なし | オン | H1/H4 |
| 3 | 120×2 | 250 | なし | オン | H1 |

| 8 | 120×1 | 500 | Bluetooth | オフ | H3 |

## 結果

### 2026-09-13 実機ラン1（Xcode 接続、DEBUG、`1077cd14`）

前段の不具合: 初版（`fe6ad744`）は `DispatchSource` を `resume()` しておらず、振動が一切鳴らず
Stop 時の `timer = nil`（サスペンド中ソースの解放）でクラッシュした。`1077cd14` で修正後の計測。

| 条件 | 間隔(ms) | 再生 | 画面/appState | fired(累計) | skipped | lateP50(ms) | lateP95(ms) | lateMax(ms) | 体感 |
|---|---|---|---|---|---|---|---|---|---|
| 120BPM×4, click | 125.0 | なし | オン/active | 80（10秒時点） | 0 | 1.2 | 3.8 | 25.2 | 1回ずつしっかり区別できた・もう少し強めが欲しい |
| 同上（継続） | 125.0 | なし | オン/active | 160（20秒時点） | 0 | 1.2 | 2.0 | 25.2 | 同上 |

- 10 秒あたり 80 回＝理論値 8 回/秒と一致し、スキップ無し。
- マトリクス #4（167ms）より短い 125ms 間隔でも、アプリ側の発火スケジュールは破綻していない。
- 注意: 遅延は `play()` 呼び出し直前までの値。
- 体感（ユーザー報告）: 125ms 間隔の `click` は1回ずつしっかり区別できた。
  → **H1 は採用**（想定の 250ms より短い 125ms でも抜け・まとまり無し、画面オン・再生なし条件）。
- 体感の強さは「もう少し強め」が希望。watchOS に強度 API は無いため、対策候補は
  (a) より強い `WKHapticType`（start / directionUp / notification 等、ただし振動長が長く高速テンポで
  連結する恐れ）、(b) 本体設定「サウンドと触覚」の触覚の強さ・はっきりとした触覚（ユーザー側設定）、
  (c) 強拍のみ強いタイプ・細分は click の使い分け。(a) の各タイプの体感強度と、連結しない最短間隔は未計測。

### 2026-09-13 実機ラン2（ユーザー体感報告、ログ数値は未取得）

- 振動タイプ比較: `failure` が「ベースの表現」に良い（`click` より強く、ビートの土台として自然）。
- 再生しながら（スピーカー／Bluetooth）の振動: 問題なく併用できた（音の途切れ・ダッキングの報告なし）。
- 画面オフ（バックグラウンド）: 振動は継続できなかった（「バックグラウンドは無理」）。

## 結論

- **H1 採用**: 125ms 間隔でも個別の振動として知覚できる（画面オン・再生なし）。
- **H2 採用**: 再生と同時に振動させても再生は妨げられない（ユーザー体感）。
- **H3 棄却済み**: 音声バックグラウンド再生中でも、画面オフでは振動を継続できない。
  本実装は「アプリが前面表示中のみ振動」を前提とし、バックグラウンド継続を再調査しないこと
  （別方式＝ワークアウト等の専用セッション流用は、音楽アプリ用途として不適切なため対象外）。
- **H4 採用（画面オン時）**: 予定時刻→`play()` 直前の遅延は p95 ≤ 3.8ms、max 25.2ms。
- 振動タイプは `failure` を基調とする。強度 API は無いのでタイプ選択で強さを出す。
- ユーザー判断により本実装へ昇格（2026-09-13）。ビート位置の検出は iPhone 側で行う。

### 追記（2026-09-13）: 機能は取り下げ — 持続的な振動は表現できない（棄却済み）

- 本実装（iPhone の低音オンセット検出＋振動データ転送、Watch の再生同期発火、再生画面のオン/オフ、
  iPhone の一括送信）まで完成させたが、使ってみて **「長く震わせ続けられない」** ことがユーザー判断で
  致命的と分かり、機能一式を revert した。
- 根拠: watchOS で使えるのは `WKHapticType` の短い固定パターンを 1 回ずつ発火する API だけで、
  振動の長さ・持続・強弱を制御できない（Core Haptics は watchOS 非対応）。低音に合わせて「ブーッ」と
  鳴らし続けるような持続的な表現は、短い振動の連打でしか近似できず、音楽的な体感にならない。
- **再調査しないこと**: watchOS の公開 API が変わらない限り、「曲に合わせて持続的に振動させる」
  系の機能は実現できない。検出側（`bass-onset-detector-design.md`）の知見は、将来 iPhone 等
  Core Haptics が使える端末で振動させる場合にのみ再利用候補になる。
- 残したもの: 本ノートと検出器の設計ノート、計測ハーネス（`tools/onset-timing-harness/`）、
  DEBUG 用 Haptics Lab（`UX-Music-Watch/WatchHapticLab.swift`）。
- 戻したコミット: `9cde69bd`（iPhone 一括送信 UI）、`172915f5`（Watch オン/オフボタン）、
  `96819ba3`（検出・転送・Watch 再生同期の本体）、`33329c71`（進捗表示の修正）。
